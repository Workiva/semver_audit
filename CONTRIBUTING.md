# Contributing to semver-audit

:wave: Thanks for your interest in semver-audit development! See the following document for getting the development environment setup, and some of the high level architecture of the system.

## Development

- Install [bun](https://bun.sh/) runtime: `curl -fsSL https://bun.sh/install | bash`
  - _See [why bun](#why-bun) for reasoning and restrictions around this js runtime_
- Install dependencies: `bun install`

```console
$ bun test # runs tests
$ bun build # builds node executable
$ bun dev # runs cli using bun runtime (better performance)
$ bun format # formats code
```

### Functional Tests

semver-audit contains functional tests which run the full stack of indexing and diffing source code. See `test/functional/<language>` for the current setup

All functional tests can be regenerated by executing

```console
bun run test:functional
```

## Architecture

For a deeper dive into semver-audit architecture, please see the `/doc` [folder](/doc/)

### Why `bun`?

[Bun](https://bun.sh/) is a modern javascript runtime, written in zig. It is known for its performance and simplification of the increasingly convoluted js ecosystem

There are a few things to note about this decision

- Bun _is not_ [boring technology](https://mcfunley.com/choose-boring-technology). It is a bleeding edge, v1, and not mature
- Bun is repeating some of the same mistakes that have [plagued the js ecosystem](https://dev.to/thejaredwilcurt/bun-hype-how-we-learned-nothing-from-yarn-2n3j)
- Semver-audit's choice to use bun is not about performance, its exclusively for creating a good development experience during development

Given the above points, there should be no leaking of bun concepts outside of the semver-audit codebase. The released artifact should only be executable using `node`, or a native exec, no bun [APIs](https://bun.sh/docs/runtime/bun-apis) should be used, and there should always be an option to switch from bun to a different technology without effecting active consumers.
